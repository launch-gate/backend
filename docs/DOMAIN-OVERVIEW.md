# Launch Gate: домены и логика платформы

Этот документ описывает уже реализованный бэкенд платформы Launch Gate с учетом текущей структуры модулей, схем БД и endpoint'ов.

## 1. Общая идея платформы

Launch Gate - это платформа для проведения конкурсов, акселераторов и хакатонов. Она закрывает полный цикл работы:

- регистрация пользователей;
- создание и настройка конкурса;
- регистрация участников в конкурс;
- сборка команд;
- настройка этапов и полей сдачи;
- прием решений команд и участников;
- проверка работ экспертами;
- сопровождение команд менторами;
- аналитика и выгрузка результатов.

Ключевая модель платформы построена вокруг конкурса, его этапов и stage submission. Именно stage submission является основной единицей проверки, менторинга и чтения результатов.

## 2. Модульная структура

Проект не разбит на микросервисы. Это единое приложение, но с раздельными Maven-модулями и отдельными схемами PostgreSQL.

### `launch-gate-app`
- запускаемый модуль;
- поднимает Spring Boot приложение;
- содержит Flyway миграции.

### `launch-gate-common`
- общие исключения;
- общие типы ответа.

### `launch-gate-identity`
- регистрация и логин;
- JWT access token;
- профиль пользователя;
- контакты пользователя;
- хранение access token в БД.

Схема БД: `identity`

### `launch-gate-contest`
- конкурс;
- организаторы и их роли;
- этапы конкурса;
- поля формы этапа;
- ресурсы этапа;
- регистрация участников в конкурс;
- команды и join request.

Схема БД: `contest`

### `launch-gate-submission`
- проект участника или команды;
- черновики и финальные stage submission;
- значения полей формы;
- чтение stage submission для разных ролей.

Схема БД: `submission`

### `launch-gate-evaluation`
- назначения экспертов;
- черновики экспертной проверки;
- публикация итоговой оценки;
- отдельный модуль AI review с HTTP-интеграцией во внешний python-сервис.

Схема БД: `evaluation`

### `launch-gate-mentoring`
- назначение менторов на команды;
- комментарии менторов по stage submission;
- календарь созвонов.

Схема БД: `mentoring`

### `launch-gate-file-storage`
- загрузка файлов;
- хранение метаданных файлов;
- генерация download URL из MinIO.

Схема БД: `file_storage`

### `launch-gate-export`
- аналитика конкурса;
- экспорт рейтинга;
- кастомная выгрузка как placeholder job.

Схема БД: `exporting`

## 3. Роли и права

### Базовые типы аккаунтов
- `PARTICIPANT`
- `ORGANIZER`

### Роли внутри конкурса
- `CREATOR`
- `ADMIN`
- `EXPERT`
- `MENTOR`

Spring Security используется для базового разграничения доступа по роли аккаунта. Более точная проверка на принадлежность к конкретному конкурсу делается через `ContestRolePolicy`.

## 4. Модель конкурса

### 4.1 Contest

Конкурс хранит:
- название;
- описание;
- правила;
- режим участия: `INDIVIDUAL` или `TEAM`;
- размер команды;
- даты;
- контакты;
- статус.

Статусы конкурса:
- `DRAFT`
- `PUBLISHED`
- `RUNNING`
- `FINISHED`

Важно:
- регистрация начинается с `startsAt`;
- отдельного `registration_starts_at` нет;
- черновой конкурс не виден участникам как рабочий сценарий.

### 4.2 ContestOrganizer

Организаторы конкурса хранятся отдельной связующей сущностью. В `contest` больше нет поля `creator_id`: источник истины по ролям только таблица `contest_organizers`.

### 4.3 ContestRegistration

Регистрация участника в конкурс - отдельная бизнес-сущность, а не обычный `@ManyToMany`, потому что у нее есть собственное поле `registeredAt`.

Для командных конкурсов регистрация является обязательным шагом перед:
- созданием команды;
- входом в команду;
- отправкой join request;
- просмотром списка участников.

## 5. Этапы и форма сдачи

### 5.1 ContestStage

Этап - это отдельная часть конкурса со своим:
- названием;
- описанием;
- правилами;
- дедлайном;
- дополнительной информацией;
- типом шкалы оценки;
- флагом `eliminating`.

Этапы имеют `sortOrder`, который начинается с `0`. Логика перестановки унифицирована через `BaseOrderEntity` и `SortOrderService`.

### 5.2 SubmissionField

Каждый этап содержит одну форму сдачи. Поля формы задаются организатором.

Поддержанные типы полей:
- `TEXT`
- `LINK`
- `GITHUB_REPOSITORY`
- `FILE`
- `FILES`
- `PHOTO`
- `VIDEO`
- `NUMBER`

У поля есть:
- название;
- тип;
- обязательность;
- список допустимых форматов файлов;
- ограничение на размер файла;
- список опций;
- подсказка участнику;
- пример заполнения;
- скрытая заметка для эксперта;
- список `criteria`.

Важно:
- таблица `evaluation_criteria` больше не используется;
- критерии проверки вынесены в отдельную таблицу `contest.field_criteria`;
- у одного `SubmissionField` может быть несколько критериев проверки;
- критерии упорядочиваются внутри поля через собственный `order`;
- для upload-полей разрешен только whitelist форматов:
  - документы: `DOC`, `DOCX`, `PDF`, `TXT`, `PPTX`, `CSV`, `XLSX`
  - изображения: `JPG`, `JPEG`, `PNG`, `WEBP`
  - видео: `MP4`, `MOV`, `WEBM`
- creator не может выбрать произвольный формат вне этого whitelist;
- при сохранении `SubmissionValue` backend сразу валидирует формат и размер файлов под конфигурацию поля;
- есть отдельный endpoint со справочником поддержанных форматов, чтобы фронтенд не дублировал enum вручную.

### 5.3 ContestResource

Ресурсы теперь существуют только на уровне этапа. У конкурса отдельного набора ресурсов нет.

Ресурс этапа может быть:
- `TEXT`
- `LINK`
- `FILE`

У ресурса есть:
- порядок;
- название;
- описание;
- ссылка;
- `fileId`, если ресурс связан с файлом.

## 6. Команды

Команды используются только в конкурсах с `TEAM` режимом участия.

### Реализованная логика
- участник должен сначала зарегистрироваться в конкурс;
- участник может состоять только в одной команде внутри одного конкурса;
- лидер команды создается вместе с командой;
- join by invite работает по invite token;
- join request можно отправить в команду;
- лидер команды может:
  - смотреть pending join request;
  - approve;
  - reject.

Дополнительно в коде защищены важные сценарии:
- нельзя создать две pending-заявки в одну и ту же команду;
- нельзя вступить сразу в несколько команд одного конкурса.

## 7. Проекты и stage submission

### 7.1 Project

`Project` - это рабочее пространство участника или команды внутри конкурса.

Project создается:
- для одного участника в индивидуальном конкурсе;
- для команды в командном конкурсе.

Внутри project нет бизнес-полей вроде полного описания проекта. Основные данные живут в формах этапов.

### 7.2 StageSubmission

Для каждого этапа внутри проекта есть отдельная сдача:
- сначала черновик;
- затем финальная отправка.

Участники заполняют значения по полям этапа, после чего:
- можно сохранять draft;
- лидер команды публикует финальную submission;
- после `SUBMITTED` редактирование блокируется.

### 7.3 SubmissionValue

Каждое поле формы хранит свое значение:
- `valueText` для текстовых данных;
- `fileIds` для файлов.

Required-поля валидируются при финальной отправке.

## 8. Проверка экспертами

Модель проверки упрощена:
- есть `review_assignments`;
- assignment хранит и назначение, и draft/final состояние проверки;
- отдельной таблицы `expert_reviews` нет;
- отдельной таблицы `criterion_scores` нет.

Эксперт работает только с конкретным `stage submission`.

Поддержаны сценарии:
- назначить эксперта;
- получить свои assignment;
- открыть выданную ему submission;
- сохранить draft score/comment;
- опубликовать итоговую оценку.

AI review теперь вынесен в отдельный модуль `launch-gate-ai-evaluation`. Он умеет:
- получать сохраненный AI review по submission;
- запускать проверку по критериям поля;
- работать с текстом, текстовыми файлами и GitHub-репозиториями;
- сохранять результаты по каждому полю и каждому критерию отдельно.
- использовать отдельный HTTP endpoint для проверки репозитория и отдельный endpoint для проверки текста.

### 8.1 Поддержанный flow AI review

Рабочий сценарий такой:
- organizer или expert открывает конкретный `stage submission`;
- фронтенд сначала вызывает `GET /organizer/evaluations/{submissionId}/ai-review`;
- если review уже был сохранен, UI показывает готовые результаты;
- если review нет, пользователь нажимает кнопку запуска AI review;
- фронтенд вызывает `POST /organizer/evaluations/{submissionId}/ai-review`;
- backend собирает все поля submission и обрабатывает их по стратегиям;
- результаты сохраняются в БД и сразу возвращаются в ответе.

### 8.2 Какие данные реально отправляются в AI сервис

Сейчас backend умеет отправлять только:
- текст, введенный прямо в форму;
- текстовые документы `DOC`, `DOCX`, `PDF`, `TXT`;
- GitHub repository URL для поля типа `GITHUB_REPOSITORY`.

Что происходит с остальными форматами:
- если поле не поддерживается для AI review, оно не ломает весь сценарий;
- backend сохраняет статус `UNSUPPORTED_FORMAT` на уровне поля и критериев;
- пользователь все равно получает полный общий результат review.

### 8.3 Правила запуска AI review

- если у поля нет ни одного критерия, оно получает `SKIPPED_NO_CRITERIA`;
- если у поля нет данных, оно получает `SKIPPED_NO_DATA`;
- если GitHub URL невалидный или репозиторий недоступен, поле помечается как `FAILED`;
- если внешний AI сервис временно недоступен, backend сохраняет `FAILED`, но не прерывает обработку остальных полей.

## 9. Менторинг

Ментор назначается не на submission, а на команду.

Поддержаны сценарии:
- организатор назначает ментора команде;
- ментор видит свои команды;
- ментор открывает team stage submission;
- ментор пишет комментарии под stage submission;
- ментор назначает созвоны;
- ментор и команда читают расписание созвонов.

Важно:
- комментарии ментора больше не привязаны к отдельным полям;
- они живут списком на уровне этапа команды и сортируются по убыванию даты.

## 10. Файлы

Файлы грузятся через MinIO.

Поддержаны сценарии:
- upload файла;
- хранение метаданных в БД;
- получение download URL;
- дальнейшая привязка файла к resource или submission value через `fileId`.

## 11. Экспорт и аналитика

Организатор может:
- получить аналитический snapshot по конкурсу;
- скачать рейтинг в `CSV` или `XLSX`;
- создать custom export job.

Custom export пока работает как placeholder job с preview-текстом. Это подготовка под будущую AI-адаптацию формата выгрузки.

## 12. Что важно понимать про текущую архитектуру

### 12.1 Основная рабочая единица
Главная единица чтения и проверки - это не весь конкурс и не abstract project, а конкретный `stage submission`.

### 12.2 Разделение read-сценариев по ролям
Чтобы не размывать права доступа, чтение реализовано через разные endpoint'ы:
- участник читает свой project;
- организатор читает stage submission организаторской ручкой;
- эксперт читает submission через assignment;
- ментор читает submission своей ручкой.

### 12.3 Упор на простую модель
В последних изменениях сознательно убраны:
- `platformId`;
- contest-level resources;
- отдельные criteria tables;
- избыточные review tables.

Итоговая модель проще, чище и лучше отражает реальный рабочий процесс платформы.
